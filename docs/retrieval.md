# LearnForge Retrieval Layer (Milestone M2)

> **Milestone:** M2 — Retrieval only.
> Takes a user query and returns the most relevant KB records **with their metadata
> intact**, for M3 (evidence / confidence / contradiction assessment) to decide what
> to do with them. **M2 does not decide answers.**
>
> Supplements `docs/architecture.md` (M0) and `docs/data-schema.md` (M1); neither is
> rewritten. Supplied KB files remain read-only.

---

## 1. Layout

```
learnforge/
  embed.py       # local embedding model + on-disk embedding store
  lexical.py     # Okapi BM25 lexical index (stdlib only)
  retrieval.py   # Retriever (dense + BM25, RRF fusion), RetrievalResult, CLI
tests/
  test_retrieval.py   # 47 pytest tests
data/processed/
  kb_records.json     # M1 output (input here)
  kb_embeddings.json  # generated by M2
requirements.txt
```

Build the embedding store (re-run whenever M1 output changes):

```
python -m learnforge.embed
```

Run a query (manual verification):

```
python -m learnforge.retrieval --query "Can I get a refund after 20 days?" --k 5
python -m learnforge.retrieval --query "FAQ-08" --mode lexical --json
```

Run the tests:

```
python -m pytest tests -q        # M1 (43) + M2 (47) = 90 tests
```

## 2. Embedding model (local)

| Property | Value |
|---|---|
| Model | `sentence-transformers/all-MiniLM-L6-v2` |
| Runtime | local, CPU (`device="cpu"`) |
| Dimension | 384 |
| Normalization | L2 (`normalize_embeddings=True`) ⇒ cosine = dot product |
| Network | **none** — `HF_HUB_OFFLINE=1` / `TRANSFORMERS_OFFLINE=1` are forced unless `LEARNFORGE_ALLOW_MODEL_DOWNLOAD=1` |
| Storage of model | `~/.cache/huggingface` (outside the repo; **not committed**) |

This follows the M2 directive for a **local** embedding model with **no external
embedding API and no API key**. Note the M0 ambiguity recorded in §9.

Embeddings are computed over each record's verbatim `chunk_text` (heading included),
matching M0 §16's "one record == one chunk".

## 3. Local storage

A **single JSON file**, `data/processed/kb_embeddings.json` — the "small local
embedding store (single JSON/Parquet file …)" M0 §16 proposed. No vector database,
no server, no index service.

```json
{
  "embedding_store_version": "m2",
  "embedding_model": "sentence-transformers/all-MiniLM-L6-v2",
  "dimension": 384,
  "normalized": true,
  "metric": "cosine",
  "record_order": ["FAQ-01", "..."],
  "vectors": { "FAQ-01": [ "... 384 floats ..." ] }
}
```

`record_order` is asserted to match the M1 record order exactly. `Retriever.from_store()`
refuses to run if the store was built with a different model than the query embedder.

Reproducibility: no clocks, randomness, or network are used. Vectors are
deterministic for a given model + torch build; the store records the model name so
regeneration is detectable.

## 4. Semantic retrieval

Cosine similarity between the (normalized) query vector and every record vector —
a single matrix–vector product, exact and deterministic:

```
semantic_score(record) = cosine(embed(query), embed(record.chunk_text))
```

## 5. Lexical retrieval

A **dependency-free Okapi BM25** index (`learnforge/lexical.py`) over
`source_id + title + chunk_text`, so record IDs ("FAQ-08"), titles, product terms,
and rare policy phrases are all lexically searchable.

Parameters are the **standard** BM25 values, not tuned: `k1 = 1.5`, `b = 0.75`.
Tokens are lowercased alphanumeric runs (internal hyphens kept, e.g. `14-day`,
`faq-08`), with a documented standard English **stopword list** removed so shared
interrogatives ("can", "i", "do") cannot give almost every FAQ record a small
lexical score.

## 6. Hybrid fusion

M0 §16 proposed "optionally a light lexical fallback" but specified **no fusion
method and no weights** (see §9). M2 forbids inventing arbitrary weights, so the
fusion is **Reciprocal Rank Fusion (RRF)** — a standard, weight-free rank-combination
method:

```
fused(record) = Σ_signals   1 / (RRF_K + rank_signal(record))
RRF_K = 60            # the standard RRF constant
```

Ranking rules (all documented in code):

1. A signal only contributes **documents it actually matched** (score > 0). Without
   this, an exact-ID query like `FAQ-08` — which scores 0.0 on BM25 for every other
   record — would let unrelated records outrank the true match via tie-breaks.
2. **Exact-ID priority**: if the query explicitly names a record ID (`FAQ-08`,
   `policy 02`, `ticket-11`), that record is placed first. This implements M0 §16's
   stated purpose for the lexical fallback; dense similarity is uninformative for
   bare IDs.
3. Ties break by ascending `source_id`, so ordering is fully deterministic.

Both individual signals stay visible on every result, so the ranking is explainable:

```
semantic relevance (cosine) + lexical relevance (BM25) = RRF ranking
```

## 7. Top-k and parameters

| Parameter | Default | Notes |
|---|---|---|
| `k` (top-k) | 5 | `search(query, k)`; `k <= 0` → `[]`; `k > 40` returns all 40 |
| `RRF_K` | 60 | standard RRF constant |
| `candidate_pool` | 10 | per-signal candidate pool fed into fusion |
| BM25 `k1`, `b` | 1.5, 0.75 | standard, untuned |
| stopwords | standard list | documented in `learnforge/lexical.py` |

`candidate_pool = max(candidate_pool, k)` so a large `k` never truncates candidates.

## 8. Why stale evidence is retained / why authority is not a filter

- **`is_stale = true` is never a deletion criterion.** Stale records are exactly
  what M3 needs to detect contradictions (e.g. the archived 7-day refund article
  vs. the current 14-day policy). Tests assert stale records are retrievable and
  keep their `stale_reason`.
- **Authority (`policy=3, faq=2, ticket=1`) is preserved but never used to filter
  or demote.** A historical ticket may be the most relevant evidence for an
  exception/conflict question (e.g. TICKET-03 for "refund after 20 days"). Tests
  assert all three authority tiers stay reachable and that a low-authority ticket
  appears alongside high-authority policy for the refund query. Weighing them is
  M3's job.
- **`contradiction_topics` are hints only**, not ground truth and not a filter.
- **No sufficiency/confidence threshold** is applied in M2; scores are exposed so
  M3 decides.

## 9. M0 ambiguities and how they were resolved (reported, not silently changed)

1. **Embedding model.** M0 §16 said embeddings would come from "a free-tier
   embedding model from the same provider family (e.g. … the provider's embeddings
   endpoint)" — i.e. an **external API**. M2 explicitly requires a **local** model
   with no external embedding API and no API key. M2's directive was followed
   (it is also consistent with M0 §5 NFR-4, "prefer local / no external calls",
   and with M0's dependency-light/locally-runnable goal). The chosen local model
   (`all-MiniLM-L6-v2`) replaces the unspecified provider-embedding idea; the LLM
   provider decision for M4 is unaffected.
2. **Fusion method / weights.** M0 proposed dense retrieval *plus* an "optional
   light lexical fallback" but named no fusion method and no weights. RRF was
   chosen (weight-free, standard) and is documented above; M0's "fallback for
   exact IDs" intent is implemented as explicit exact-ID priority.
3. **Top-k.** M0 did not specify a `k`; 5 was chosen as a small, documented default.

## 10. Limitations

- **One record = one chunk** (per M0): long policy records are retrieved as a whole,
  so a query hitting one paragraph still returns the entire record. Chunk
  refinement is a future improvement, not an M2 change (M0 fixed the chunking).
- **No re-ranking model** (a cross-encoder exists in the local cache but M0/M2 did
  not call for one; adding it would be an unapproved technology change).
- **For bare-ID queries**, the remaining top-k slots after the exact-ID hit are
  filled by weak semantic matches — inherent to "no threshold in M2"; M3's
  sufficiency logic handles them.
- **Floating-point reproducibility** holds for a fixed torch/model build; a
  different torch version may change the last digits of a cosine score (the model
  name recorded in the store makes such drift detectable).
- **Embeddings are not incremental**: `python -m learnforge.embed` rebuilds all 40
  vectors. At this corpus size that is instantaneous; an incremental path is a
  future improvement.
- **Latency**: the first model load in a process takes a few seconds; retrieval
  itself is a single matrix product over 40 rows.
